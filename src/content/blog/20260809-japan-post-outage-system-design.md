荷物は郵便局にある。局員もいる。トラックも動いている。
それなのに、受け取れない。

2026年8月7日から8日にかけて日本郵便で起きたシステム障害は、そういう形の障害でした。モノの流れは何ひとつ止まっていないのに、情報が止まった瞬間に、モノが動かせなくなった。

「システムの話は難しそう」と思われるかもしれません。でもこの障害は、専門用語をひとつも使わずに説明できます。そして説明してみると、これがまったく他人事ではないことが分かります。ネットショッピングをする人にとっても、システムを作る人にとっても。

## 何が起きたのか

まず、報道されている事実を時系列で整理します。

| 時刻 | 出来事 |
| :-- | :-- |
| 8/7 4:00頃 | データを送受信するシステムで機器が故障 |
| 同上 | 通販大手との「荷物の情報のやりとり」が停止 |
| 以降 | 受け取りに必要な問い合わせ番号・パスワードのメールが送れない状態に |
| 8/8 午前 | 徐々に復旧。約1日遅れでメールが順次届き始める |
| 8/8 21:00前 | 日本郵便が障害の解消を発表 |

発生から解消の発表まで、およそ **41時間**。影響は全国に及び、郵便局・コンビニ・宅配ロッカー「はこぽす」での受け取りができなくなりました。原因は、この記事を書いている時点で「調査中」とされています。

## 止まったのは「情報」だけだった

この障害でいちばん興味深いのは、**止まったものと、止まらなかったものの境界**です。

```
   通販の会社
      │
      │  ← ここが切れた（荷物の情報のやりとり）
      ▼
   日本郵便のシステム
      │
      │  ← 連鎖して止まった（受け取り番号を知らせるメール）
      ▼
   あなたのメールボックス
      │
      ▼
   郵便局 / コンビニ / はこぽす
   ↑ 荷物はここにある。棚に載っている。局員もいる。何も壊れていない
```

配送網も、倉庫も、窓口も、一切壊れていません。壊れたのは、情報をやりとりする機械が一台。それだけです。

にもかかわらず、末端の「荷物を受け取る」という行為が、全国規模でできなくなった。

例えるなら、**マンションの部屋の前まで荷物が届いているのに、オートロックの解錠番号を知らせるメールが届かないので誰も入れない**、という状態です。荷物にも建物にも問題はない。でも入れない。

現代のシステムでは、こういう構造がとても増えました。デジタルが、物理的なモノの「門番」になっている。門番が一人倒れると、その先にある大量のモノが、まるごと動かせなくなります。

> ここから先、システムの内部で何が起きていたかについては、公開されている情報からの推測を含みます。日本郵便の実際の作りを断定するものではありません。「同じ形の障害を、自分たちが作らないために」という視点で読んでください。

## なぜ「メールが送れない」が「荷物を受け取れない」になるのか

今回いちばん効いてしまったのは、ここだと思います。

報道によれば、受け取りに必要な **問い合わせ番号とパスワードが書かれたメール** が送れなくなったことで、受け取りができなくなりました。つまり、こうなっていたと推測されます。

> メールが届く　＝　荷物を受け取れる
> メールが届かない　＝　荷物を受け取れない

ここに、設計上の弱点が隠れています。

### メールは「確実に届く」ものではない

メールというのは、本質的に「たぶん届く」程度の信頼性しかない仕組みです。遅れることもあるし、迷惑メールフォルダに入ることもあるし、送信する側の設備が止まることもある。

にもかかわらず今回は、そのメールに **「あなたが受取人本人である」ことを証明する鍵** が載っていて、しかもそれ以外の入手経路が用意されていなかった。だから、メールが止まっただけで、荷物の受け渡しという業務そのものが止まりました。

さきほどのマンションの例えを続けるなら、**合鍵を宅配便で送っている**ようなものです。その宅配便が遅れたら、家に入れない。

本来やるべきなのは、**鍵は最初から金庫に入れておいて、メールでは「金庫に鍵が入りましたよ」と知らせるだけにする**ことです。こうしておけば、メールが1通も届かなくても、自分でアプリやマイページを開いて番号を確認しに行けます。

メールはあくまで「お知らせ」であって、「唯一の受け渡し経路」にしてはいけない。これが原則です。

### 自分の身の回りにも同じ構造がある

これは郵便に限った話ではありません。

- パスワードを忘れたときの再設定リンク
- ログイン時に届く6桁の確認コード
- 電子チケットのQRコード
- 決済完了の通知

このあたりは、どれも「メールやSMSが届かなかったら詰む」設計になりがちです。サービスを作る側の人は、一度自分のプロダクトでこう問いかけてみてください。

> **メールの送信機能を今この瞬間に止めたら、使えなくなる機能はどれか。**

そこに出てきた機能が、メールという不確実なものに命綱を預けている部分です。

## なぜ復旧に41時間もかかったのか

機器が壊れること自体は、避けられません。ハードディスクは壊れるし、部品は劣化する。設計で決まるのは「壊れてから何時間で戻るか」だけです。

41時間という数字は、こう分解できます。

> **気づくまでの時間　＋　判断する時間　＋　実際に直す時間　＝　41時間**

### 発生したのが午前4時だった

これが地味に大きい。人がいちばん少ない時間帯です。

システムには、壊れたら自動で予備に切り替わる仕組み（自動切り替え）を持たせることができます。でもその引き金を人間が引く設計になっていると、深夜の復旧時間は「機械を切り替える時間」ではなく、**「担当者が起きて、状況を把握して、決断するまでの時間」**になります。

予備の機械を用意していても、それを使う判断が人任せなら、夜間の復旧はどうしても遅くなる。

### 「完全に壊れる」より「半分だけ壊れる」ほうが厄介

もうひとつ、この手の障害で本当に厄介なのがこれです。

- システムは動いている
- 「調子はどう？」と聞けば「正常です」と答える
- 通信もできる
- **でも、データが流れていない**

完全に電源が落ちてくれたほうが、実は気づくのは簡単なんです。中途半端に生きている機械は、「壊れている」と判定されないまま、静かにデータを飲み込み続けます。

電話に例えるなら、**繋がってはいるけれど、こちらの声が相手にまったく届いていない**状態です。相手は無言のまま。こちらは「聞こえてますか？」と言い続けるけれど、それすら届いていない。

### 「機械が動いているか」ではなく「仕事が進んでいるか」を見る

だから、システムの見張り方には工夫が要ります。

工場に例えると分かりやすい。ベルトコンベアが回っているかどうかを見ても、あまり意味がありません。**出口から製品が出てきているか**を見るべきです。コンベアは回っているのに、途中で詰まっていて製品が一個も出てこない、ということは普通に起きます。

システムでも同じで、見るべきなのは「機械の電源が入っているか」ではなく、こういう数字です。

- 直近5分で、何件の荷物情報を処理できたか
- 直近5分で、何通のメールを送れたか
- **いちばん古い「まだ処理できていない仕事」は、何分待たされているか**

3つめが、経験上いちばん効きます。理由は3つあります。

**理由1: 原因が何であれ、必ずこれに現れる。** データベースが遅い、外部との通信が詰まっている、処理する担当プログラムが止まっている、同じ仕事を延々やり直している — どれであっても「待たされている時間」は伸びます。

**理由2: 誤報が少ない。** 正常なときはほぼゼロに張り付くので、「10分を超えたら異常」といった線引きがしやすい。

**理由3: 「ゼロ件」を検知できる。** これが決定的です。「エラー率」のような指標は、そもそも処理が1件も流れなくなると計算できなくなり、**完全に止まったときに限って警報が鳴らない**という最悪の挙動をします。「待たされている時間」なら、止まれば止まるほど数字が伸びていくので、確実に鳴ります。

午前4時に壊れて、誰も気づかないまま朝を迎える。それを防ぐのは、だいたいこの一本の見張り役です。

## 実は、評価すべき点もある

報道の中に、地味だけれど設計上とても重要な記述があります。

復旧後、**約1日ほどの遅れで、メールが順次届くようになった**という点です。

これは、**障害の間に届いた荷物の情報が、失われていなかった**ことを意味します。どこかにきちんと溜まっていて、復旧後にそれを流し直せた。もしデータが消えていたら、「どの荷物が誰宛てなのか分からなくなりました」という、比較にならない大事故になっていたはずです。

これは、システムの作り方でいうと **「送信箱」方式** と呼べるものです。

郵便局の窓口を想像してください。お客さんから預かった手紙は、まず必ず「これから送る手紙」の箱に入れる。実際に配達する担当が休んでいても、箱に入れる作業だけは続けられる。担当が戻ってきたら、箱に溜まった分を順番に配達する。

こうしておけば、配達側が41時間止まっても、預かった手紙は1通も失われません。

### ただし、溜まった分をそのまま全部流してはいけない

ここが、復旧作業の難しいところです。

41時間分の未処理が積み上がった状態で、復旧した瞬間に全部を一気に流すと、こういうことが起きます。

**1. 送り先を殺してしまう。** メール配信の設備や、通販会社側のシステムが、普段の何十倍もの量を一度に浴びて、今度はそちらが倒れます。復旧作業が次の障害を生む、という典型的なパターンです。

**2. 受信箱が溢れる。** 同じ荷物について「到着しました」「保管期限が近づいています」「まもなく返送されます」が数秒差で届く。ユーザーからすれば何が起きているのか分かりません。

**3. もう意味のない通知が届く。** 41時間の間に、自分で問い合わせて解決していたり、荷物が返送されていたりします。そこに今さら「到着しました」と届いても、混乱を招くだけです。

だから、溜まった分を流すときは意図的に **「まとめて、間引いて、ゆっくり」** やる必要があります。同じ荷物についての通知は最新の1通だけに畳む、古すぎて意味を失ったものは送らない、普段の処理速度を大きく超えない速さで流す。

「復旧しました」で終わりではなく、**復旧のさせ方まで含めて設計する。** ここまでやって、初めて障害対策と言えます。

## 「システムが使えないときの手動運用」は用意されていたか

今回、もし窓口に「システムが使えないときは、身分証と伝票番号を確認して手渡しする」という代替手段が用意されていたら、影響はかなり小さくできたはずです。

多くの現場で、こうした代替手段は「そのとき現場が頑張る」という形で暗黙的に存在しています。でもそれは、用意されているとは言えません。

例えるなら、**非常階段**です。建物には必ずありますが、普段使わないので、気づくと荷物が積まれていたり、扉が開かなくなっていたりする。いざ火事になったときに初めて「通れない」と分かる。

システムの代替手段も、まったく同じです。**年に一度しか通らない道は、必ず腐ります。** 使っているうちに周りの部品が入れ替わって、いざ使おうとしたときには動かなくなっている。

だから、代替手段は定期的に「実際に通してみる」必要があります。三ヶ月に一度は本番と同じ条件で切り替えてみる、日常の点検項目に組み込む。避難訓練とまったく同じ発想です。

## お知らせ自体が、障害で止まっていないか

最後に、地味ですが効く話を。

利用者が本当に困るのは「使えないこと」よりも、**「使えない理由が分からないこと」**です。

荷物が受け取れない人は、何度もサイトを読み込み直し、コンビニに足を運び、コールセンターに電話をかけます。この二次的な負荷が、必死に復旧作業をしている現場をさらに削っていきます。

だから、障害を知らせる手段は、**障害を起こしているシステムと切り離しておかなければいけません。**

- 障害情報のページを、本番システムと同じ場所に置かない
- 障害のお知らせを、いま止まっているメール設備で送ろうとしない
- お知らせを更新するのに、止まっているログイン機能を必要としない

「メールの仕組みが止まったので、メールでお知らせできません」というのは笑い話に聞こえますが、事前に整理していないと普通に起こります。

## 確認しておきたい9つの問い

システムを作る立場の方向けに、チェックリストにまとめます。**「はい」が並ぶほど危険**です。

| # | 問い | 「はい」だと何が危ないか |
| :-- | :-- | :-- |
| 1 | メールを止めたら、使えなくなる機能があるか | 不確実な連絡手段に業務を預けている |
| 2 | 受け取り番号やコードを、利用者が後から自分で確認できないか | 通知が唯一の受け渡し経路になっている |
| 3 | 「動いているのにデータが流れていない」状態を見抜けないか | 半分壊れた状態に気づけない |
| 4 | 「いちばん古い未処理の仕事が何分待っているか」を見ていないか | 完全に止まったときに警報が鳴らない |
| 5 | データを受け取った記録と、通知の送信が一体になっているか | 送信に失敗するとデータごと消える |
| 6 | 復旧時に、溜まった分を無制限に流す作りになっているか | 自分で次の障害を作る |
| 7 | 手動での代替手段を、直近3ヶ月で一度も実行していないか | 非常階段が塞がっている |
| 8 | 障害情報のページが、本番と同じ場所に載っているか | 障害を知らせられない |
| 9 | 深夜の切り替えに、人間の判断が必要か | 復旧時間が人の応答速度になる |

9つのうち、いくつ「大丈夫」と言い切れるでしょうか。私は自分のプロダクトを見返して、4番と7番で手が止まりました。

## おわりに

今回の件を「大企業の古いシステムの話」として片づけてしまうと、何も残りません。

**モノの流れは無事なのに、情報の一点が詰まったせいで全体が止まる。** この形の障害は、システムを部品に分けて連携させている限り、規模を問わず誰にでも起こります。むしろ、きれいに分割されたシステムほど、「細い連絡経路が業務全体を人質に取る」構造を作り込みやすい。

そして利用者の側から見れば、教訓はもっとシンプルです。**受け取り番号やコードが「メールにしか存在しない」サービスは、そのメールが止まった瞬間に手も足も出なくなる。** そういうときのために、注文履歴や配送業者の追跡ページから自分で情報を辿れる経路を、普段から確認しておくと少し安心です。

きれいに分けたつもりのシステムが、実は連絡経路1本で繋がったままになっていないか。
一度、自分の関わっているサービスの全体像を思い浮かべて、線を引いてみてください。
