サイトのプラグインを全部最新にしても、今回の穴はふさがりません。

2026年10月21日、Webサイトを動かす土台である **PHP** そのものに、深刻な脆弱性が2件公開されました。研究者たちが付けた名前は「**PHP2Shell**」。条件がそろうと、**ログインもせずに、外からサーバーを乗っ取られる恐れ**があります。

私はふだんReactやNext.jsで開発していて、昨年12月にはReactの脆弱性「React2Shell」を解説しました。名前は似ていますが、今回はPHPの話です。そして影響の広さは、今回の方がずっと大きいかもしれません。WordPressをはじめ、世の中の多くのWebサイトがPHPの上で動いているからです。

この記事では、エンジニアではない人にも伝わるように、専門用語をできるだけ使わずに整理します。

> この記事は、2026年10月21日夜（日本時間）時点の公開情報をもとにしています。状況は数時間単位で変わっているので、対応するときは記事末尾の一次情報を必ず確認してください。

## 何が起きたのか

まず事実を整理します。

| 項目 | 内容 |
| --- | --- |
| 通称 | PHP2Shell |
| 識別番号 | CVE-2026-109618 / CVE-2026-109619（2件） |
| 深刻度 | 9.2（10点満点。区分は「緊急」） |
| 影響 | 認証なしで、サーバー上で好きなプログラムを動かされる恐れ |
| 対象 | PHP 8.2.35 / 8.3.36 / 8.4.27 / 8.5.12 より前のバージョン |
| 修正版の公開 | 2026年10月21日 23時ごろ（日本時間） |

「好きなプログラムを動かされる」は、セキュリティの世界でいちばん重い部類の被害です。サイトの書き換え、保存されている情報の持ち出し、サーバーを踏み台にした別の攻撃まで、何でもできてしまうからです。

![PHP2Shellが公開されるまでの流れを示す時系列の図。8月に研究者がPHPの開発チームへ報告、10月20日に情報が漏れ、10月21日の正午ごろ（日本時間）にCloudflareが防御ルールを有効化、同日23時に修正版が公開された](/images/articles/20261021-php2shell-explained/timeline.webp)

経緯にも少し特徴があります。研究者たちは8月の時点でPHPの開発チームに報告し、本来は修正版を出すまで伏せておく約束でした。ところが公開予定日の前日、10月20日に情報が漏れてしまいました。開発チームは予定を前倒しして、21日に修正版を出しています。

情報が漏れてから修正版が出るまでのあいだにも、攻撃の試みが観測されたと複数のセキュリティ企業が報告しています。図の右端、「修正版が出た」時点ですでに、攻撃する側も動き始めていた、ということです。

## なぜ「サイトを最新にしても」防げないのか

ここが今回いちばん大事なポイントです。

Webサイトは、何層かに重なってできています。いちばん上に、WordPressやLaravelで作られた「サイトそのもの」があり、その下で、サイトのプログラムを読んで実行する **PHP** が動いています。さらにその下に、サーバーのOSがあります。

![Webサイトの層を示す図。上から「サイト（WordPress・プラグイン・テーマ）」「PHP本体」「サーバー（OS）」の3層があり、真ん中のPHP本体の層にだけオレンジ色で穴が描かれている。サイトの層を更新しても、穴のある層には届かない](/images/articles/20261021-php2shell-explained/layers.webp)

今回の穴があるのは、真ん中のPHPの層です。

家に例えると、壁紙や家具（サイト）をどれだけ新しくしても、**土台（PHP）にひびが入っていれば直らない**のと同じです。WordPressの本体やプラグインをすべて最新にしても、この穴はふさがりません。PHPそのものを新しいバージョンに入れ替える必要があります。

もう一つ厄介なのは、**サイトのプログラムが動き出す前に攻撃が成立してしまう**ことです。研究者の報告では、サイトに届いたデータをPHPが受け取って整理している段階、つまりサイトの中身が「このリクエストを受け付けるかどうか」を判断するより前に、穴を突けるとされています。サイト側でどれだけ丁寧に入力をチェックしていても、そのチェックが始まる前に事が起きてしまいます。

## 穴の正体を、ホテルの客室で例えると

技術的な中身にも少しだけ触れておきます。分かりにくければ、この章は読み飛ばしても大丈夫です。

PHPは、たくさんの人からの注文（リクエスト）をさばくために、作業担当（ワーカー）を何人か用意して、**同じ担当を次々に使い回します**。1件終わるたびに担当を作り直していたら、遅くて仕方がないからです。

ホテルの客室に置き換えると分かりやすくなります。

![ホテルの客室の例え話の図。左は正常な流れで、1人目の客が使ったあと清掃が終わってから2人目の客が入る。右は今回の問題で、清掃が途中で打ち切られたまま、前の客の鍵やメモが残った部屋に次の客が通される](/images/articles/20261021-php2shell-explained/hotel-room.webp)

客室は、前のお客さんが帰るたびに清掃して、まっさらにしてから次のお客さんを通します。これが本来の流れです。

ところがPHPには、**緊急事態が起きると、作業をその場で打ち切って飛び出す**仕組みがあります。たとえばメモリ（作業に使える机の広さ）が足りなくなったときです。今回見つかったのは、この「打ち切り」が、清掃の途中や、部屋の準備がまだ終わっていないタイミングで起きると、**片付けが中途半端なまま次のお客さんを通してしまう**という問題でした。

部屋には前のお客さんの鍵やメモが残っています。攻撃者はまず、わざと机が足りなくなるような大きな注文を送って、清掃を途中で打ち切らせます。そのうえで次の注文を送り、散らかったままの部屋を自分の都合のいいように使います。2件の脆弱性は、どちらもこの「中途半端な後片付け」に関わるものです。

研究者の報告によれば、引き金になるのは、ファイルをアップロードするときなどに使う、ごく普通のフォーム送信の形式です。特別な設定をしていない、初期状態のPHPでも届いてしまう、とされています。

なお、発見したセキュリティ企業のWizは、AIを使って短期間で攻撃手順を作れたと説明しています。一方で、メモリ不足で処理を危ないタイミングで打ち切らせる手口そのものは、2004年にもPHPの脆弱性として報告されています。新しいのは穴そのものより、「古い弱点を、実際に使える攻撃にまで組み立てる速さ」なのかもしれません。ここは公開情報からの私の推測を含みます。

## 自分は関係ある？ 立場別にやること

ここからは、読んでいる人の立場ごとに整理します。

![立場別の対応をまとめた図。レンタルサーバーやホームページ制作会社に任せている人は事業者のお知らせを確認、WordPressなどを自分のサーバーで動かしている人はPHPを修正版に更新して再起動、PHPが入った機器や製品を使っている人はメーカーの更新情報を確認する](/images/articles/20261021-php2shell-explained/who-should-act.webp)

### レンタルサーバーや制作会社に任せている人

ブログやお店のサイトを、レンタルサーバーやホームページ制作会社に任せている人は多いと思います。この場合、PHPを入れ替えるのは基本的に事業者の側です。自分でできることは次の2つです。

- 契約しているレンタルサーバーや制作会社の「お知らせ」「障害・メンテナンス情報」を確認する
- 管理画面でPHPのバージョンを選べるサービスなら、修正版が配られているかを確認し、古いバージョンを選んだままにしない

数日のあいだ、サイトが一時的に止まるメンテナンスが入るかもしれません。それは多くの場合、事業者が穴をふさいでいる作業です。

### 自分でサーバーを管理している人

PHPを **8.5.12 / 8.4.27 / 8.3.36 / 8.2.35 以降** に更新し、Webサーバーとワーカーを再起動してください。PHPの開発チームは「修正版への更新が、唯一の完全な対策」と明言しています。

いくつか、つまずきやすい点があります。

| 注意点 | 理由 |
| --- | --- |
| 更新したら必ず再起動する | 動いたままのワーカーは古いPHPのまま |
| サーバーに入っているPHPを全部確認する | 複数のバージョンが入っていることがある。コマンドで表示される1つだけでは足りない |
| Linuxの配布元のパッケージは、バージョン番号だけで判断しない | 古い番号のまま修正だけを取り込んでいることがある。更新履歴に今回の識別番号があるかで確認する |
| Dockerのイメージは作り直す | 古いイメージを使い続けると、穴の空いたPHPのまま動き続ける |
| PHP 8.1以前は公式の修正版が出ていない | すでにサポートが終わったバージョン。配布元の対応を確認しつつ、移行を急ぐ |

すぐに更新できない場合の一時しのぎとして、PHPの開発チームはメモリ上限や「アップロードの進み具合を記録する機能」を止める設定などを挙げています。ただし、**どれも不完全で、1つだけでは2件のうち片方にしか効かない**とも書かれています。あくまで更新までのつなぎです。具体的な設定は、記事末尾の公式アドバイザリを読んでください。

### PHPが中に入っている機器や製品を使っている人

PHPは、Webサイトだけでなく、ルーターの管理画面や業務用のソフトウェアの中で動いていることもあります。利用者からは見えないことが多いので、使っている製品のメーカーが更新情報を出していないか確認してください。IPA（情報処理推進機構）も、この点に注意するよう呼びかけています。

## 更新したあとに確認しておきたいこと

PHPを新しくすれば、これからの攻撃は防げます。ただ、**更新する前にすでに入り込まれていた場合、その痕跡は消えません**。

泥棒が入ったあとに鍵を替えても、家の中に仕掛けられたものはそのまま残ります。それと同じです。

![鍵を替えた家の例え話の図。玄関の鍵は新しくなっているが、家の中には以前に置かれた不審な箱が残っている。更新は新しい侵入を防ぐが、すでに仕掛けられたものは自分で探して取り除く必要がある](/images/articles/20261021-php2shell-explained/after-patch.webp)

サーバーを管理している人は、更新のあと数日は次のような点を気にかけておくと安心です。

- 見覚えのないファイルが、サイトのフォルダに増えていないか
- WordPressなどに、知らない管理者アカウントが増えていないか
- メモリ不足のエラーや、サーバーエラー（500番台）が急に続いていないか
- 不審な点があれば、データベースのパスワードやAPIの鍵を新しいものに替える

もう一つ、SNSなどで「攻撃を再現するプログラム」をうたうものが出回っています。中身が本物かどうか分からないうえ、ウイルスが仕込まれている可能性もあります。**「自分のサイトで試してみよう」と動かさない**でください。

## おわりに

今回の件で改めて感じたのは、自分が書いたプログラムの下にも、たくさんの「誰かが作った土台」があるということです。

私自身、ふだんの開発ではフレームワークやライブラリの更新には気を配っていても、その下で動く実行環境のバージョンまでは、毎日意識しているわけではありません。サイトを最新にしたつもりでも、土台が古ければ守れない。今回の脆弱性は、それをはっきり見せてくれたと思います。

サイトを自分で運営している人も、誰かに任せている人も、まずは「自分のサイトはどのPHPの上で動いているのか」を一度確認してみてください。それが分かっていれば、次に同じようなことが起きたときも、落ち着いて動けるはずです。
