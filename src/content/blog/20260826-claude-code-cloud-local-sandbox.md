普段、記事のネタ集めから下書きまでをCowork（クラウドで動くClaude Code）に任せています。ネタ受信箱に放り込んだメモを拾って、下書きを書いて、公開してはいけない情報が入っていないかをチェックして、公開済みフォルダに置く。ここまでは何十本も問題なく回ってきました。

ところが先日、いつも届く完了報告の代わりに「訂正」という件名のメールが届きました。開いてみると、直前の記事（OpenAIのAPIキー漏洩に気づいた話）の下書きは完成しているのに、そこから先の公開作業がまるごと止まっている、という内容でした。

## 「リポジトリが見つからない」という誤報から始まった

最初の報告には「ブログのリポジトリが接続フォルダの中に見当たらない」と書かれていました。おかしいな、と思って確認を求めたところ、すぐに訂正が届きました。リポジトリは `/Users/yuki/dev/yuki-dev-blog` にちゃんとあり、画像生成やX投稿に使う`.env`のキーも、node・npm・gitも全部揃っていた、最初にフォルダを探索したタイミングがマウント検出より早かっただけだった、という訂正でした。

正直、ここで「なんだ、単なる凡ミスか」と流しかけたのですが、訂正メールにはもうひとつ、もっと大事な情報が書かれていました。材料は全部揃っていたのに、公開作業そのものが実行できなかった、という事実です。

## 本当の原因は「GitHubしか通っていなかった」

調べてもらうと、原因はコードの不具合ではありませんでした。この処理を動かしているCoworkのサンドボックス自体が、公開に必要な外部サービスへの接続を許可していなかったのです。

到達できたのは `github.com` だけ。ヒーロー画像を生成する `api.openai.com`、ブログのデプロイを確認する Vercel のURL、記事を公開する `zenn.dev`、告知を投稿する `x.com` と `api.x.com` は、どれも接続できませんでした。

途中、画像生成コマンドが `sharp` モジュールのネイティブバイナリ不整合で落ちて、一瞬「これが原因か」と思ったのですが、それを直した後も `fetch failed` で止まりました。DNSレベル・curlレベルでも到達性がないことを確認してあったので、リトライで直る一時的な不調ではなく、環境そのものの制約だと判断したそうです。ちなみに原因調査の過程で `package.json` に一時的な差分が出たものの、元の内容に戻して `git status` がクリーンなことまで確認してから報告してきました。この「余計なものを残さずに、止まった理由だけを正直に報告する」姿勢は、地味に信頼できるポイントだと思っています。

## クラウドとローカルは「賢さ」ではなく「繋がる場所」が違う

この一件で改めて言語化できたのは、クラウドのClaude CodeとローカルのClaude Codeの違いは、頭の良さでも実行速度でもなく、**どのネットワークの内側で動いているか**だということです。

クラウド側（Cowork）は隔離されたサンドボックスの中で動いていて、接続していい外部サービスがあらかじめ絞られています。これは制約というより安全設計で、勝手にどこへでも通信できてしまう方がむしろ怖い話です。一方でローカル側は自分のPCの回線をそのまま使うので、自分がブラウザで開けるサイトには基本的に全部届きます。どちらのClaude Codeも同じように賢く動いてくれるのですが、「今どの網の中で作業しているか」によって、できることの範囲がまったく変わってきます。これに気づかずに「クラウドに任せれば全部終わるはず」と思い込んでいたのが、今回の一番の見落としでした。

## 使い分け方: 下書きまではクラウド、対外公開はローカル

そこで今のパイプラインは、意図的に二段構えにしています。

クラウド（Cowork）には、ネタ受信箱のチェック、下書きの執筆、frontmataの整形、公開してはいけない情報が混ざっていないかのチェック、下書きフォルダから公開済みフォルダへの移動までを任せています。ここは自分のVault内のファイル操作と、せいぜいGitHubへのpushくらいしか要らない工程なので、クラウドのサンドボックスでも完結します。

そこから先、ヒーロー画像の生成、ブログのデプロイ確認、Zennへの公開、Xへの告知投稿は、フルにインターネットへ出られる自分のPCのClaude Codeに引き継ぐようにしました。クラウド側が止まったときは、実行記録とメールで「どこまで終わっていて、何が原因で、何が残っているか」を報告してもらい、それを合図に手元のClaude Codeが`publish-from-draft`という手順で続きを拾います。実際、今回のOpenAIキー漏洩の記事もこの流れで、画像生成のクレジットを追加してもらった後に手元側が引き継ぎ、ブログ・Zenn・Xまで問題なく公開まで終わりました。

## 教訓: 自動化は「途中で気持ちよく止まれる」ように作る

一つの環境に全工程を無理やり詰め込もうとすると、届かない外部サービスに当たった瞬間にパイプライン全体が意味不明な形で失敗します。それよりも、「ここまではクラウド、ここから先はローカル」という境界線をあらかじめ決めておいて、境界を越えるタイミングで人間が読める報告を挟む方が、結果的に壊れにくいと感じています。

今回も、サンドボックスの制約に気づかずゴリ押しで解決しようとしていたら、原因調査中の一時的な差分をそのまま残してしまっていたかもしれません。止まったときに正直に止まって、状況を正確に報告してくれたおかげで、実リポジトリに変な傷を残さずに済みました。Claude CodeやCoworkで公開まわりの自動化を組んでいる人は、「クラウドのサンドボックスは自分のPCと同じネットワークにいるわけではない」という前提を、一度どこかで確認しておくと良いと思います。
