9月4日にClaude Code v2.1.260のリリースノートを読んでいて、目が止まった一文がありました。Edit・Write・Readの権限ルールに指定したパスに括弧が含まれていると、そのルールが無効な設定として無視されるかBashのサンドボックスチェックをすり抜けてしまい、読み取り専用にしていたはずのフォルダが実際には書き込み可能だった、というバグ修正です。自分は普段、Claude Codeに画像生成からブログのビルド・デプロイ、Zenn連携、X投稿までを任せていて、触ってほしくない場所には権限ルールで蓋をしているつもりでいました。その「つもり」が、書式次第では最初から効いていなかったかもしれないと気づかされた話です。

## 何が起きていたのか

公式のリリースノートを確認すると、パスに括弧が含まれるEdit・Write・Readの権限ルールが、無効な設定として落とされるかBashのサンドボックスに無視される形で機能していなかったと説明されています。同じリリースでは、zshの特定の変数にコマンド置換を忍ばせることで承認プロンプトを自動的にすり抜けてしまう別の脆弱性も一緒に修正されていました。フォルダ名に環境名やバージョンを括弧書きで添える命名は珍しくないので、思い当たる人は少なくないはずです。権限まわりの見えない穴が、同じリリースで2つ同時に塞がれた形になります。

## 自分がまさに「任せている」当事者だった

自分はpublish-from-draftというスキル経由で、Claude Codeに画像生成・ブログの同期とデプロイ・Zenn連携・X投稿までを日常的に任せています。任せる以上、触ってほしくない場所は権限ルールで区切って、そこから先は信じて手を離しているつもりでした。ところが今回のバグは、その「信じて手を離している」設定自体が、パスの書き方によっては最初から機能していなかった可能性があるという話です。自分が普段どんな権限ルールを書いているか、恥ずかしながらしばらく見返していません。任せることと、任せた設定が実際に機能しているかを確かめることは、別の話だったのだと気づかされました。

## 確認できていないことを、そのまま書く

このバグを知ってすぐに思ったのは、自分の設定ファイルに括弧入りのパス指定がないか確かめたい、ということでした。ただ、この記事を書いているCoworkの環境からは手元のリポジトリの設定ファイルに直接アクセスできず、今この場で確認することはできませんでした。「確認した結果、該当なしでした」ときれいに締めくくりたい気持ちはありましたが、実際に確認していないことを確認できたことにして書くのは違うと思うので、正直に書いておきます。次に手元のClaude Codeを開いたときに、真っ先に見返すつもりです。

## 「効いていると思い込んでいた」は今回が初めてではない

振り返ると、この感覚には覚えがあります。Zennへの公開処理が、設定上は「公開済み」の状態になっているのに実際には反映されていなかった件も、設定上は正しく見えるのに実際には動いていなかったという意味で同じ構造でした。AIエージェントに任せる作業が増えるほど、「設定した通りに動いているはず」という前提そのものを時々疑ってみる必要があるのだと思います。今回はたまたま公式のリリースノートで気づけましたが、気づかないまま動き続けているルールが他にもあるかもしれません。次に手元の設定を見返すところから、確かめていきます。
