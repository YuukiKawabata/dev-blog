# publish-article

ネタを受け取って、**本人の声で**記事を書き、どこに出すかを決めて、公開まで運ぶ。

## 前提となる構造

**記事のマスターは Obsidian。** ブログリポジトリはその同期先にすぎない。

```
Obsidian /個人/発信/記事/公開済み/     ← 記事の正本。ここに書く
        ↓  npm run sync:obsidian （rsync --delete）
yuki-dev-blog/src/content/blog/        ← 同期先
        ↓
   ブログ / Zenn / X / note
```

`sync-obsidian.sh` は `rsync --delete` で同期する。つまり **Obsidian に無い記事はブログから消える。**
ブログ側に直接書いて終わりにすると、次の同期で消滅する。必ず Obsidian に書く。

## 全体の流れ

```
ネタ → ⓪人格の読み込み → ①事実確認 → ②タイプ判定 → ③執筆 → ③.5本文の画像 → ④X投稿の執筆 → ⑤自己点検
        ↓
        ⑥Obsidianへ配置 → ⑥.5ヒーロー画像を生成・確定 → ⑦ブログ同期・公開 → ⑧デプロイ待ち
        ↓
        ⑨Zenn → ⑩X → ⑪note → ⑫記録（記事実績CSV・記事研究・state.json）→ ⑬報告
```

**本文には画像を入れる。** 文字だけの記事にしない。読者が状況を思い浮かべられるよう、
③.5で実画面のキャプチャや比較画像を集めて本文に差し込む（2026-10-12 ユーザーの指示）。

**画像は⑥.5で確定させてから、どこかに公開する。** ブログ・Zenn・Xのどれか1つでも
公開する前に画像を揃える。以前は「Xの手前でだけ画像を待つ」運用だったが、
公開状態がプラットフォームごとにバラバラになる方が扱いづらいのでやめた。

**スキルが発動したこと自体が公開の承認。** 途中で確認を求めずに最後まで走らせる。
ユーザーはネタを渡した時点で公開を意図している。

### ただし、以下に当たったら必ず止めて報告する

これは承認ゲートではなく安全弁。**黙って進むと取り返しがつかないもの**だけを列挙している。

| 条件                                                        | なぜ止めるか                       |
| ----------------------------------------------------------- | ---------------------------------- |
| `自分/セキュリティと公開ルール.md` に触れる内容が入っている | 実名発信。出したら検索結果に残る   |
| 一次情報の裏が取れない事実がある                            | 誤情報を本人の名前で出すことになる |
| `sync:obsidian` で**削除の差分**が出た                      | 他の記事が消える                   |
| Zenn の差分が新規1本以外にも出た                            | 意図しない記事の書き換え           |
| 辛口の線引き（個人攻撃・政治・災害・他人の炎上）に触れる    | 炎上リスク                         |
| Obsidian が読めない（iCloud未同期）                         | 人格を読まずに書くことになる       |
| 記事の中の数字・実績が Obsidian で裏取りできない            | 経歴の捏造になる                   |

止めるときは、何が引っかかったかを具体的に示す。「念のため確認します」で止まらない。

## ⓪ 人格の読み込み（省略しない）

`references/persona.md` を読み、そこに挙がっている Obsidian のノートを実際に読む。

これを飛ばすと「よくできたAIの記事」になる。本人の発信として出す以上、ここが一番重要。
**人格の定義は Obsidian が正本**なので、スキル内の写しではなく必ず現物を読む。

## ① 事実確認

ネタがニュースやURLなら、**一次情報を複数ソースで裏取りする**。WebSearch と WebFetch を使う。
渡されたURL1本だけを信じて書かない。日付・数字・固有名詞は特に間違えやすい。

裏が取れなかったことは書かない。推測は本文中で「公開情報からの推測を含む」と明示する。
特定の企業や個人の内部事情を断定しない。設計論・一般論に昇華させる。

**本人の経歴や実績の数字は捏造しない。** Obsidian に書いてある実数だけを使う。

## ② 記事タイプの判定

`references/routing.md` を読んで A〜D を決める。ここで配信先がほぼ決まる。

- **A. 技術解説・設計論・ニュース考察** → ブログ + Zenn + X
- **B. 個人開発の裏側・プロダクト開発記** → ブログ + note + X
- **C. 速報・短い気づき** → X のみ（記事にしない）
- **D. キャリア・お金・働き方** → note + ブログ

## ③ 記事の執筆

`references/writing.md` を読んでから書く。

記事の声は **ですます調・一人称・実体験ベース**。X の常体とは別物なので混ぜない。
トーンはプロフェッショナル寄り。前職の話や自虐オチで落とさない（Obsidian `SNS/私について.md` の軸とトーン）。
既定は「コード例なし・非エンジニアにも分かる」。技術的な深さは落とさず、例え話で伝える。

**書く場所**: `Obsidian /個人/発信/記事/下書き/YYYYMMDD-<英語スラッグ>.md`

まず `下書き` に書き、自己点検を通ってから `公開済み` へ移す。こうすると、点検前の記事が
同期で誤ってブログに出ることがない（`sync-obsidian.sh` は `公開済み` だけを見る）。

## ③.5 本文の画像を集める（省略しない）

`references/writing.md` の「本文の画像」を読んでから集める。

- **目安は3〜6枚、h2のおよそ1つにつき1枚。** 数字を出す章には、その数字が写っている実画面を置く
- 撮るもの: App Store Connect・アナリティクス・管理画面、公開ストアページ、アプリやWebの実画面、変更前後の比較
- ログインが必要な画面は Claude in Chrome（本人のChrome）で開き、`zoom` + `save_to_disk` で必要な範囲だけ切り抜く
- 保存先は `public/images/articles/<basename>/<内容が分かる名前>.webp`（`cwebp -q 85〜90`）
- 本文には `![何が写っているかを具体的に書いた説明](/images/articles/<basename>/<name>.webp)` で差し込み、
  直前か直後の文で「何を見てほしいか」を一言添える
- **キャプチャの数字と本文の数字を一致させる。** 撮った時点でデータが進んでいたら、本文の数字か期間の書き方を直す
- 撮れないときは止まらない。公式ページのスクショ（出典を本文に明記）か、`artifact-diagramming` などで作った図で補う。
  それも無理なら、報告で「何章に画像が無いか・なぜか」を書く

## ④ X の告知を書く（1投稿・自動生成に任せない）

**記事の告知は1投稿だけ。返信でつなげるスレッドにしない**（2026-10-14 ユーザーの指示）。
返信の連なりは読まれず、1投稿目で興味を持たれなければ記事も開かれない。

書き方は `references/persona.md` の「記事告知の投稿」に従う。要点:

- **1行目で、記事の中でいちばん「えっ」となる出来事を短く言い切る。** 外の話や前置きから入らない
- **気になる言葉を1つ立てる**（例: 「.envを勝手に上書きされた」「APIキーが全部消えた」）。説明より事件
- **短く、平易に。** 全体で100〜140字が目安。専門用語は1つまで。手順や仕組みの説明は記事に任せる
- 常体。絵文字なし。自分を落とすオチにしない
- 最後の行に記事のURLを置く（リンクカードが出る）

書けたら frontmatter の `x.thread` に**要素1つ**で入れる。これで自動生成（見出しからの複数投稿）が上書きされる。

```yaml
x:
  thread:
    - "AIに.envを勝手に上書きされて、APIキーが全部消えた。\nOpenAIとXのキーを取り直す羽目になった話と、AIに値を見せずに書き戻した方法を書いた。\nhttps://dev-blog-pi-six.vercel.app/blog/<basename>/"
```

URLは素のブログURLで書けばよい。`sync-x` が `utm_source=x` を自動で付ける（2026-10-14〜）。
URL入りの投稿は1件$0.20。

## ⑤ frontmatter を組み立てて自己点検

キーの有無がそのまま配信先になる。

```yaml
---
title: '...'
description: '...' # 検索結果とOGPに出る。1〜2文
pubDate: 'YYYY-MM-DD'
heroImage: '/images/hero/YYYYMMDD-<スラッグ>.webp'
tags: ['...']
categories: ['Development']
author: 'Yuki'
zenn: # ← あれば Zenn に配信
  slug: '...'
  emoji: '📦'
  type: 'tech'
  topics: ['...', '...']
  published: true
x: # ← あれば X に配信
  slug: '...'
  mode: 'digest'
  thread: ['...'] # 本人の声で書いた告知1投稿（URL入り）
  article_enabled: false # 既定。代表作だけ true
note: # ← あれば note に配信
  tags: ['個人開発']
---
```

`x.article_enabled` は通常 `false`。X Articles はタイムラインに流れず「記事」タブにしか出ないため、
到達は告知の投稿が担う。代表作だけ `true` にする。判断基準は `references/routing.md`。

公開前に、生成物を自分で点検する。ここは止まるためではなく、**壊れたものを出さないため**。

```bash
npm run sync:x     # 告知投稿と content_state の生成（ネットワークなし）
npm run sync:note  # note に出す場合
```

自己点検の項目:

- `references/persona.md` の「AIっぽさが出る典型」に当てはまっていないか
- 絵文字が入っていないか。ハッシュタグは本人が使う系統か
- 告知が1投稿で、1行目に事件が来ているか。短く平易か（140字前後）。常体か
- 公開ルールに触れる情報が入っていないか
- CTAのURLが絶対URLで、実在するか
- 本文に画像が入っているか（目安3枚以上）。画像のパスが実在し、代替テキストが具体的か
- キャプチャに個人情報・APIキー・他人のアカウント・非公開の数値が写っていないか

引っかかったら**書き直す**。直せないものだけ止めて報告する。

ヒーロー画像は `heroImage` に想定パスを書いておく。実体は次の⑥.5で作る。

## ⑥〜⑪ 公開

`references/publishing.md` の手順に従う。**順番に意味がある。**

- ⑥.5で画像が確定する前に、ブログ・Zenn・Xのどれにも公開しない
- ブログが公開されデプロイが完了する前に X へ投稿すると、CTAリンクが404の記事を出すことになる

⑥.5のヒーロー画像は `npm run generate:hero -- --slug <basename> --theme "..."` で
OpenAI（既定）を使って自動生成する。スタイルはスクリプトに固定してある（ブログのデザインに合わせた、
紙色の背景・墨色の線・オレンジ1点のフラットなイラスト）。`--theme` には文字ではなく
**描いてほしい物を具体的に**書く（例:「無地の本が並ぶ本棚で、2冊だけ少し前に出ている」）。APIキーが無い、または2回連続で失敗したら、
ユーザーに手動での用意を依頼して止まる。詳細は `references/publishing.md`。

## ⑫ 記録（省略しない）

`references/review.md` に従い、記録を残す。

- `個人/発信/記事/実績/記事実績.csv` — 1行追記。X告知の投稿URLは「X告知URL」列に入れる
- `個人/発信/記事/記事研究.md` — 研究ログに、その日の学びと仮説（A番号）を追記
- `.x/state.json` — コミットして push する（忘れると次回二重投稿する）

SNS側の台帳・投稿実績CSV（`SNS/99_システム/`）は 2026-10-03 の運用切り替え（v7）で廃止された。
書かない。旧データは `SNS/_バックアップ_v6_2026-10-03/` にあり、触らない。

**ユーザーは結果を見ていない前提で動く。** 記録しなければ学習は起きず、
同じ失敗を繰り返す。ここを飛ばすくらいなら公開を遅らせる方がまだよい。

## ⑬ 報告

`references/publishing.md` の完了報告フォーマットに従う。推測ではなく実際に確認した結果を書く。

## よくある失敗

過去に実際に起きたもの。

- **ブログ側に直接記事を書いた** → `sync:obsidian` の `--delete` で消える。記事は Obsidian に書く
- **Xのスレッドを自動生成のまま投稿した** → 見出しの番号列挙＋絵文字で、本人のルール違反かつAI臭
- **Xの告知を5投稿のスレッドにし、1投稿目を外の話から始めた** → 「全く気にならない」「難しくて長い」（2026-10-14）。
  告知は1投稿で、1行目に事件を置く
- **前職（コンビニ店長）のネタや自虐オチで締めた** → 2026-10 の方針変更に反する。古い Obsidian ノートや過去の投稿案ログに引きずられやすい
- **curl で x.com の200を見て「投稿成功」と判断した** → SPAなので常に200。確認は必ずブラウザで
- **ブログのデプロイを待たずにXへ投稿した** → CTAリンクが404だった
- **`.x/state.json` をコミットし忘れた** → 次回に二重投稿する
- **X Articles が「投稿されていない」ように見える** → 「記事」タブにあるだけ。仕様
- **画像が無いままXへ投稿した** → リンクカードは投稿時にキャッシュされ、後から画像を足しても
  遡って反映されない。貼り直す以外に直せない。**⑥.5で画像を確定させてから、どの媒体にも公開しない**
- **本文が文字だけだった** → 数字や画面の話をしているのに、読者が想像するしかなかった。③.5で実画面を入れる
- **ヒーロー画像がブログのデザインと合っていなかった／英字が崩れていた** → 旧スタイル（暗い背景・青紫のグラデーション）では
  ブログの紙色・オレンジ1色と合わず、背表紙に「Producticy」という崩れた英字も出た（2026-10-12）。
  生成後に画像を開き、文字が描かれていたら⑥.5の判断基準どおり作り直すか手動に切り替える
- **画像生成APIのレスポンス形式を検証せずに実装した** → Gemini の画像生成は複数のAPI仕様が
  混在しており（旧 generateContent と新 Interactions API）、ドキュメントの自動要約だけでは
  誤った内容が混ざることがある。実際のAPIキーで一度検証するまでは「動くはず」と言い切らない
- **Zennで本文の画像が出なかった／既存記事40本に差分が出た** → 当時の `sync:zenn` は画像を運ばず、UTMを全記事に付けていた。
  2026-10-14 に、画像の自動コピーと「新しい記事だけUTM」に直した。Zennには直近24時間の投稿数の上限があり、
  既存記事をまとめてpushすると新規記事ごと止まる（2026-10-03に17本前後が止まった）。差分が新規1本以外に出たら止める
- **`sync:obsidian` でビルドが壊れた** → Obsidian側にfrontmatterが無いファイルがあると、
  ブログ側の正しい版を上書きして消す。同期後は必ず差分を確認し、新規1本以外に
  変更が出たら止める

## 参照ファイル

- `references/persona.md` — **執筆前に必ず読む。** Obsidianのどのノートを読むか、本人の声の特徴
- `references/routing.md` — 配信先の判断基準
- `references/writing.md` — 記事の文体・構成・タイトルの付け方、本文の画像の入れ方
- `references/publishing.md` — 公開手順の詳細とコマンド
- `references/review.md` — 公開後の記録と、週次の振り返り・学習の回し方
