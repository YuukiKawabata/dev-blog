# publish-article

ネタを受け取って、記事を書き、どこに出すかを決めて、公開まで運ぶ。

このリポジトリ（`yuki-dev-blog`）は個人ブログの正本であり、Zenn・X への配信スクリプトを内蔵している。
note だけは公式APIがないのでブラウザ操作で投稿する。

## 全体の流れ

```
ネタ → ①事実確認 → ②タイプ判定 → ③執筆 → ④配信先の決定 → ⑤生成物の提示
                                                              ↓
                                                        【ユーザー承認】← 止まるのはここ1回だけ
                                                              ↓
      ⑥ブログ公開 → ⑦デプロイ待ち(200確認) → ⑧Zenn → ⑨X → ⑩note → ⑪state.jsonコミット
```

**承認前に外向きの操作は一切しない。** 承認後は最後まで自動で走らせる。
途中で失敗したら、そこで止めて何が起きたかを報告する。黙って次に進まない。

## ① 事実確認

ネタがニュースやURLなら、**必ず一次情報を複数ソースで裏取りする**。WebSearch と WebFetch を使う。
渡されたURL1本だけを信じて書かない。日付・数字・固有名詞は特に間違えやすい。

裏が取れなかったことは書かない。推測を書く場合は、本文中で「公開情報からの推測を含む」と明示する。
特定の企業や個人の内部事情を断定しないこと。設計論・一般論に昇華させる。

## ② 記事タイプの判定

`references/routing.md` を読んで、A〜Dのどれかを決める。ここで配信先がほぼ決まる。

- **A. 技術解説・設計論・ニュース考察** → ブログ + Zenn + X
- **B. 個人開発の裏側・プロダクト開発記** → ブログ + note + X
- **C. 速報・短い気づき** → X スレッドのみ（記事にしない）
- **D. キャリア・お金・働き方** → note + ブログ

## ③ 執筆

`references/writing.md` を読んでから書く。文体・構成・避けるべきことが書いてある。

**既定は「コード例なし・非エンジニアにも分かる」。** これはユーザーの明示的な方針。
技術的な深さは落とさず、例え話で伝える。コードブロックを書きたくなったら、それは例え話に置き換えられないか考える。

ファイル名は `src/content/blog/YYYYMMDD-<英語スラッグ>.md`。

## ④ 配信先の決定とfrontmatter

判定したタイプに応じて frontmatter のキーを組み立てる。**キーの有無がそのまま配信先になる。**

```yaml
---
title: "..."
description: "..."           # 検索結果とOGPに出る。1〜2文
pubDate: "YYYY-MM-DD"
heroImage: "/images/hero/YYYYMMDD-<スラッグ>.webp"
tags: ["..."]
categories: ["Development"]
author: "Yuki"
zenn:                        # ← あれば Zenn に配信
  slug: "..."
  emoji: "📦"
  type: "tech"
  topics: ["...", "..."]     # 最大5個、Zennの既存トピックに合わせる
  published: true
x:                           # ← あれば X に配信
  slug: "..."
  mode: "digest"
  description: "..."         # スレッド1投稿目。本文のdescriptionより短く、口語で
  hashtags: ["...", "..."]
  article_enabled: false     # 既定はfalse相当の運用。代表作だけ true にする
note:                        # ← あれば note に配信
  tags: ["個人開発"]
---
```

**`x.article_enabled` の既定判断**: X Articles はタイムラインに流れず「記事」タブにしか出ない。
到達はスレッドが担うので、**通常は `article_enabled: false`（スレッドのみ）**。
保存性が高く代表作になる記事だけ `true` にする。判断に迷ったら false で、理由を添えて提案する。

ヒーロー画像はユーザーが用意する。**画像がまだ無い場合は `heroImage` に想定パスを書いておき、承認を求めるときに「画像を置いてください」と伝える。**

## ⑤ 生成物の提示（ここで止まる）

外向きの操作の前に、以下をまとめて提示して承認を得る。

1. **記事タイプと配信先**（なぜそう判断したかを1〜2文で）
2. **記事本文**（ファイルに書いた上で、要点と構成を示す）
3. **Xのスレッド全文**（`npm run sync:x` を実行して `.x/drafts/<slug>.json` から取り出す）
4. **確認してほしい点**（事実の不確かな箇所、一人称で書いた実感の部分、画像の要否）

生成だけなら課金も外部送信も発生しないので、ここまでは必ず実行してから見せる。

```bash
npm run build          # frontmatterとMarkdownが壊れていないか
npm run sync:x         # スレッドと content_state の生成（ネットワークなし）
npm run sync:note      # note に出す場合
```

## ⑥〜⑪ 公開

承認を得たら `references/publishing.md` の手順に従う。
**順番に意味がある。** ブログが公開されデプロイが完了する前に X へ投稿すると、CTAリンクが404の記事を出すことになる。

## よくある失敗

過去に実際に起きたもの。同じ轍を踏まないこと。

- **curl で x.com の200を見て「投稿成功」と判断した** → x.com はSPAなので存在しないURLでも200を返す。X の確認は必ずブラウザで実際の画面を見る
- **ブログのデプロイを待たずにXへ投稿した** → CTAリンクが404だった。デプロイ完了(200)を確認してから進む
- **`.x/state.json` をコミットし忘れた** → 次回実行時に「未投稿」と誤認して二重投稿する
- **X Articles が「投稿されていない」ように見える** → 「記事」タブにあるだけ。ポストのタイムラインには流れない仕様

## 参照ファイル

- `references/routing.md` — 配信先の判断基準。記事タイプが決まらないときに読む
- `references/writing.md` — 文体・構成・タイトルの付け方。執筆前に読む
- `references/publishing.md` — 公開手順の詳細とコマンド。承認後に読む
