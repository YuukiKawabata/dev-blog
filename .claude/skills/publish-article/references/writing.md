# 記事の書き方

## 実績から分かっていること（執筆前に確認）

Zennに公開した17本の実測（2026-08-11時点）から、形式によって明確な差が出ている。
**最新の数値と仮説は `個人/発信/記事/記事研究.md` を読む。** 以下は要約。

| 形式 | n | 平均いいね |
| --- | ---: | ---: |
| **体験**（自分が使った・やった話が主） | 4 | **39.5** |
| 解説（技術やニュースの説明が主） | 8 | 5.1 |
| 比較（複数を横並び） | 3 | 3.3 |

ただし**体験型なら必ず伸びるわけではない**。体験型4本の内訳は 80 / 74 / 4 / 0 で、
形式内の分散が最も大きい。「週末に触った感想」でも0のものがある。

現時点で効いていそうな要素:

- **導入に自分の生活・立場の具体**を置く（「34歳」「子どもが寝静まった」など）。あり17.4 / なし9.1
  - 2026-10 からは、立場の具体を**エンジニア / 個人開発者としての状況**（何を作っていて、何に困ったか）で書く。前職の話や自虐には寄せない（Obsidian `SNS/私について.md` の軸とトーン）
- **h2は4〜6本**。上位4本は全てh2=4〜5。h2=1も h2=12〜13も伸びていない

これらは確定ではなく検証中の仮説。**書いたら記事研究.mdに結果を戻す**こと。

## 大方針

**技術的な深さは落とさず、専門用語に頼らない。**

これは「簡単に書く」ではない。難しいことを難しいまま説明するのは楽で、難しいことを平易な言葉で正確に説明するのが難しい。後者をやる。

読者は2種類いると想定する。

- **エンジニア**: 「その視点はなかった」と思わせたい
- **非エンジニア**: 「そういうことだったのか」と思わせたい

両方に届く記事は、具体的な事例から一般的な構造を取り出したときに生まれる。

## コード例は書かない

ユーザーの明示的な方針。コードブロックを書きたくなったら、**例え話に置き換えられないか**を先に考える。

実際に機能した置き換えの例:

| 技術概念 | 使った例え |
| --- | --- |
| 通知が業務のクリティカルパスにある | 合鍵を宅配便で送っている。届かなければ家に入れない |
| gray failure（部分故障） | 電話は繋がっているが、こちらの声が相手に届いていない |
| ヘルスチェックより業務メトリクス | ベルトコンベアが回っているかより、出口から製品が出ているかを見る |
| Transactional Outbox | 預かった手紙をまず「送る箱」に入れる。配達担当が休んでも預かりは続く |
| 使われないフォールバック経路 | 非常階段。普段使わないので荷物が積まれ、火事のとき通れない |

例え話は**読者がすでに知っている世界**から借りる。郵便・建物・工場・電話・階段。
新しい比喩を発明するより、手垢のついた比喩を正確に当てはめる方が効く。

構造図（ASCIIの矢印図）は例外的に使ってよい。コードではなく「どこが切れたか」を一目で示せる。

## 本文の画像

**本文には画像を入れる。** 数字や画面の話を文字だけで説明すると、読者は想像するしかない。
実画面を1枚置くだけで「本当にこうなっている」が伝わり、記事の信頼も上がる（2026-10-12 ユーザーの指示）。

### 何を撮るか

| 記事の中身 | 置く画像 |
| --- | --- |
| ダウンロード・売上・アクセスの数字 | App Store Connect／アナリティクス／管理画面の該当部分 |
| アプリやWebの機能 | 実機・シミュレーター・ブラウザの実画面 |
| 「変えた」「直した」話 | 変更前と変更後を1枚に並べた比較画像（ラベル付き） |
| ストアでの見え方 | 公開ストアページ（apps.apple.com など） |
| 仕組み・流れ | 自作の図（例え話を図にしたもの） |
| ニュース・他社の話 | 公式発表ページのスクショ（出典を本文に明記）。報道記事の画像は使わない |

**目安は3〜6枚、h2のおよそ1つにつき1枚。** 数字を出す章には、その数字が写っている画面を置く。
飾りの画像は入れない。1枚ごとに「この画像で何が分かるか」を言えるものだけにする。

### 撮り方

- ログインが必要な画面は Claude in Chrome（本人のChrome）で開く。内蔵ブラウザはログインしていない
- `computer` の `zoom` に `save_to_disk: true` を付けて、必要な範囲だけ切り抜く。マウスカーソルや
  ツールチップが写り込まないよう、先にカーソルを範囲外へ動かす
- 期間を指定できる画面は、URLの日付パラメータで期間を固定してから撮る
- 比較画像はPython（Pillow）で並べて、上に「変更前」「変更後」のラベルを入れる
- 保存は `public/images/articles/<basename>/<内容が分かる英語名>.webp`。`cwebp -q 85〜90` で変換する

### 写してはいけないもの

`自分/セキュリティと公開ルール.md` に従う。特に次のものは、写っていたら切り抜くか撮り直す。

- APIキー・トークン・Key ID・Issuer ID・チームID・審査用ログイン
- 個人のメールアドレス・電話・住所、家族の名前
- 他人のアカウント・他社の非公開情報、本業・副業の画面
- 方針上出さないと決めている情報（例: 前職の話）が写っている場合は、本人に確認する

### 本文への入れ方

```
![何が写っているかを具体的に書いた説明](/images/articles/<basename>/<name>.webp)
```

- 代替テキストは「App Store Connectの画面」で終わらせず、読み取れる数字や違いまで書く。
  画像が表示されない人や読み上げにも同じ情報が届くようにする
- 画像の直前か直後の文で「どこを見てほしいか」を一言添える（例:「右端の『前の期間』が、直す前の14日間の数字です」）
- **キャプチャの数字と本文の数字を一致させる。** 撮った時点でデータが進んでいたら、本文の数字か期間の書き方を直す
- 撮った日と、データがいつ時点のものかが分かるように書く（「10月10日までの90日」など）

## 構成の型

必須ではないが、これで書くと安定する。

1. **フック** — 短い断定文で始める。3行以内。読者の常識を軽く裏切る
2. **事実の整理** — タイムラインや数字を表にする。ここは淡々と
3. **問いの提示** — 「なぜそうなったのか」を明示的に立てる
4. **本論** — 見出しごとに1つの教訓。各セクションに例え話を1つ
5. **チェックリストや持ち帰り** — 読者が明日できることを表にする
6. **おわりに** — 一般化して締める。読者自身の話に引き戻す
7. **参考リンク** — 使った一次情報を列挙する

## タイトル

- **専門用語を入れない。** 「通知をクリティカルパスに置くな」より「なぜ41時間も続いたのか」
- **読者が抱く素朴な疑問**をそのまま置くと強い
- 具体的な数字が使えるなら使う
- 長くなってよいが、前半30文字で何の話か分かるようにする（Xのリンクカードで途中まで表示される）

良い例: `荷物は届いている。でも受け取れない — 日本郵便のシステム障害は、なぜ41時間も続いたのか`

## 誠実さ

- **推測は推測と書く。** 「〜と推測されます」「公開情報からの推測を含みます」を明示
- **特定の企業や個人を断定的に批判しない。** 事例から設計論を取り出す
- **一次情報にリンクする。** 記事末尾に参考リンクを置く
- **著作権に注意。** 報道記事の本文を転載しない。事実を要約して自分の言葉で書く

## 一人称

記事のどこかに1箇所、自分の実感を入れる。読者が「この人が書いている」と感じる部分になる。

例: 「9つのうち、いくつ『大丈夫』と言い切れるでしょうか。自分のプロダクトで確かめたところ、4番と7番はすぐに手を入れる必要がありました。」

自分を落として締めない。実感は「何を確かめて、どう判断したか」の形で書く。

**ただし嘘は書かない。** 実感がないなら書かない。承認を求めるときに「ここは一人称で書いたので、実感と違えば直してください」と伝える。

## X の告知

X の告知は `x.thread` に本人の声で書いた1投稿を入れる（`persona.md` の「記事告知の投稿」）。
`x.description` や h2 見出しからの自動生成は、`x.thread` が無いときの予備でしかない。使わない前提で書く。

## 見出しの付け方

見出しは、記事の目次としてそのまま読まれる。

- 見出しだけ読んで内容が推測できるようにする
- h2 は4〜6本を目安に、多くても8個以内に収める
